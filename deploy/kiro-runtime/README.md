# Kiro 受限运行环境（说明与模板）

状态：说明与模板，随 VOXWARD-SUB-016 提交。本目录不安装任何软件，不创建系统用户，不修改系统配置。每一项都标明「已实现」「部署要求」或「待实测」。部署要求不等于已完成。

适用范围：处理真实观众内容的运行时 agent（提案 §9.2）。它使用独立账号、独立工作目录和最小权限，不复用拥有源码、个人资料或治理库权限的开发 agent。

### 1.1 服务进程以独立账号启动 CLI（部署要求，待实测）

服务进程与 CLI 分属两个账号。服务账号持有业务数据与服务配置，不持有模型凭据。运行账号持有 `KIRO_API_KEY`，只拥有运行根目录与自己的 HOME。

1. 服务账号（示例名 `voxward`）运行服务进程。它不属于运行账号的用户组，读不到 `KIRO_RUNTIME_HOME` 与 `KIRO_API_KEY`。
2. 运行账号（示例名 `voxward-kiro`）拥有 `KIRO_RUNTIME_ROOT` 与 `KIRO_RUNTIME_HOME`，权限 0700。
3. 适配器的 `command` 指向一个包装程序，而不是 kiro-cli 本身。包装程序由 root 拥有、服务账号不可写，只做一件事：以运行账号执行固定路径的 kiro-cli，并原样转发参数。例如 `exec runuser -u voxward-kiro -- /opt/kiro/bin/kiro-cli "$@"`，或 `sudo -n -u voxward-kiro -- …`。服务账号经 sudoers 或等价的系统设置，只被允许执行这个包装程序。本仓库不提供包装程序与 sudoers 规则。
4. 适配器给 CLI 的环境是完整给定的（已实现：不继承服务环境）。`HOME` 与 `KIRO_API_KEY` 必须穿过包装程序到达 CLI。`sudo` 默认会重置环境变量，因此包装程序要显式保留它们（待实测）。
5. 这种分账号方式有一个代价（待实测）。运行账号的进程，服务账号既读不到它的 `/proc/<pid>/cwd`，也不能向它的进程组发信号。此时 §3 的孤儿扫描无法终止残留 CLI，只能保留目录并写入 `needs-manual.json`。要让扫描自动终止残留，需要服务账号对该进程组的信号权限，或由运行账号自己的守护单元负责终止。这一点尚未解决。

## 2. 环境变量模板

`runtime.env.example` 只含占位值。变量名不使用 `VOXWARD_` 前缀，因为服务的配置加载器会拒绝未知的 `VOXWARD_` 变量。真实值由部署的密钥库提供，不提交到仓库。

## 3. 启动与清理

- 每批结束时（成功、失败、取消、超时）先请求删除该批已保存的 CLI 会话，再删除运行目录。删除请求失败时目录保留，记录里仍有会话 ID，由孤儿扫描重试（已实现，删除效果待实测）。
- 运行流里第一次出现会话 ID 时就写入 `session.json`，服务进程中途异常退出也留下记录（已实现，`crash-drill.test.ts`）。
- 孤儿扫描 `sweepOrphanRunDirectories` 在启动时执行一次，之后由 `scheduleOrphanSweeps` 按周期执行（已实现；组合根尚未接入 Kiro 适配器，见设计文档 D3，因此目前只存在于库级接口与测试中）。
- 记录的进程仍在运行，且它的工作目录就是该运行目录（Linux 上读 `/proc/<pid>/cwd`）时，孤儿扫描才终止整个进程组：先 SIGTERM，宽限后 SIGKILL。工作目录不符的 pid 视为已被其它进程复用，不发任何信号（已实现）。
- 身份无法确认（非 Linux，或读取 `/proc` 被拒绝），或 SIGKILL 后进程仍然存在时，目录保留，并写入 `needs-manual.json`，内含原因码。这种情况需要运维处理。服务账号能否向运行账号的进程发信号取决于部署，待实测。
- 没有记录会话 ID 的孤儿，在运行目录下执行 `chat --list-sessions -f json` 查找，并逐个请求删除（待实测：输出格式未对 kiro-cli 3.1.0 核实）。列表为空表示没有会话；列表不可读时目录保留，需要运维处理。
- 本进程中仍在运行的批次，其目录不会被扫描。扫描假定同一运行根只有一个服务进程（部署要求）。
- 残留的进程组无法终止时，孤儿扫描不会强制结束其它进程，只保留目录并报告。
