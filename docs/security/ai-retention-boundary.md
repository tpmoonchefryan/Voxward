适用范围：一次性 AI 会话（提案 §8.1、§8.4）在应用侧产生的文件，以及 Kiro CLI 与模型提供方可能保留的数据。

## 3. 结果的含义

- 会话删除结果为 `DELETE_REQUESTED` 时，只表示 CLI 以退出码 0 接受了删除命令。
- 它不表示提供方已经删除数据。
- Archive、导出，或移入可恢复的回收区，都不等于删除（提案 §8.4）。
- 应用侧删除运行目录不等于提供方删除。两者分别记录，不互相代替。

## 5. 崩溃恢复路径

正常路径：批次结束时，先请求删除已记录的 CLI 会话，再删除运行目录。删除请求失败时目录保留，记录里仍有会话 ID，由孤儿扫描重试。

异常路径（服务进程在批次运行中异常退出，例如 SIGKILL、OOM 或主机重启）：

1. 会话 ID 已经写入 `session.json`。运行流中首次出现合法会话 ID 时即写入，不等进程结束。服务死掉时，CLI 进程组以 detached 方式继续运行，不会被父进程带走。
2. 孤儿扫描（启动时执行一次，之后按周期执行）逐个处理残留目录：
   - 记录的进程仍在运行，且工作目录是该运行目录（Linux 上读 `/proc/<pid>/cwd`）：先 SIGTERM，宽限后 SIGKILL 整个进程组，然后删除已记录的会话，再删除目录。
   - 记录的进程已不存在，或 pid 已被其它进程复用（工作目录不符）：不发信号，直接删除已记录的会话，再删除目录。pid 复用时不会误杀其它进程。
   - 没有记录会话 ID：在运行目录下执行 `chat --list-sessions -f json`（待实测）。列表为空表示没有会话，直接删除目录；列出的会话逐个删除；列表不可读时保留目录。
   - 身份无法确认、进程在 SIGKILL 后仍然存在、删除失败、目录删除失败、或没有可用的 CLI：保留目录，写入 `needs-manual.json`（原因码）。每次扫描都会重新判断并报告，不会静默遗留。
3. 本进程中仍在运行的批次，其目录不会被扫描。

仍未覆盖或未验证：

- 记录 pid 之前的窗口。进程刚被创建、`session.json` 尚未写入 pid 时服务崩溃，只能依靠「无记录超过 1 小时」判断，这时 CLI 是否还在运行未验证。
- 正常路径中，运行流没有给出会话 ID 时，不查询 CLI 会话列表。CLI 是否会保存不输出 ID 的会话，待实测。
- 同一批产生多个会话时，只删除已记录的首个 ID（待实测）。
- 分账号部署下，服务账号能否读取运行账号进程的工作目录并向其进程组发信号，取决于部署。见 `deploy/kiro-runtime/README.md` §1.1。不具备权限时，残留 CLI 只能保留目录并报告。
- 同一运行根只能有一个服务进程。两个服务进程同时扫描时，另一个进程的批次可能被当作孤儿。
