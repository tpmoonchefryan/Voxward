## 1. 六类平台咨询问题

### Q1 逐观众频道评分的用途与许可路径

- 问题要点：仅在同一主播频道内部，根据聊天内容审核结果维护逐观众分值，并据此决定是否进入进一步审核，是否被允许。能否通过派生指标条款和合规审核路径取得许可，或需要其他专门确认。
- 为什么要问：评分键由平台、主播频道和频道内观众主体共同确定。评分只用于该频道的审核分流，不公开排名，不跨频道共享，不用于广告定向或 CRM 销售评分（提案第 5.1、15.1 节）。计分公式为 `nextScore = clamp(currentScore + requestedDelta, minScore, maxScore)`，实际变化按钳制后的值记账。
- 现有材料：提案第 15.1 节的政策路径。派生指标补充条款页列出的示例是频道级评分，本包核对的片段中未见逐观众审核分的明确示例（见 `status-and-gaps.md` 第 5 节）。
- 缺口：没有平台结论。提案第 15.1 节写明，这些限制有助于说明用途，但不能证明自动合规。
- 希望得到的答复：该用途是否允许。若允许，需要哪些审核、申请或条款接受步骤。若不允许，平台可接受的替代形态是什么。

### Q2 观众告知与同意

- 问题要点：对观众需要何种告知或同意。主播授权能覆盖哪些处理。记分例外与删除方式是否足够。
- 为什么要问：数据面板提供“仅删除数据”和“删除并加入记分例外名单”两种操作（提案第 11.2 节）。记分例外是独立的频道偏好，不是黑名单（第 11.4 节）。开发者政策要求 API Client 提供清楚、易用的授权撤销方式（核对见 `data-processing.md` 第 5.3 节）。
- 现有材料：`data-processing.md` 第 5 节的删除与例外说明。
- 缺口：观众告知文本尚未起草。主播授权能覆盖的范围未经平台确认。提案第 11.1 节写明，自托管不自动决定所有法律角色。
- 希望得到的答复：需要的告知形式和同意类型（若需要）。主播授权能覆盖的处理范围。删除与例外机制是否满足要求。

### Q3 保留、刷新与删除要求

- 问题要点：分值、计分证据、原文和临时 ID 映射，分别适用什么保留、刷新和删除要求。
- 为什么要问：提案第 12.3 节的数值是“初始实现建议”，不是平台要求。原文、映射和校验后的 JSON 建议最多 7 天，元数据建议 30 天。提案写明，评分状态和计分账本需要明确期限，真实评分的保存期限待平台确认，不能默认无限保留。
- 现有材料：`data-processing.md` 第 4 节列出提案建议值，并列出核对到的政策条款。
- 缺口：分值和计分账本可保存的期限未知。提案第 11.3 节的“七个日历日”与开发者政策 III.E.4.g 一致，适用于用户请求删除存储数据。III.E.4.g 中的“用户”是否包括发言观众，政策原文未直接说明，需平台确认；该问题不改变 7 日期限本身。撤销授权另有 III.D.2.c 的 7 日（经应用内撤销）与 30 日（经 Google 安全设置页撤销）两种期限。
- 希望得到的答复：每类数据可保存的最长期限，刷新或删除的触发条件，以及是否需要定期核验授权是否仍有效。

### Q4 自托管分发模式的责任与覆盖

- 问题要点：自托管分发模式下，软件项目与每个部署方 Cloud 项目的审核责任和覆盖范围分别是什么。能否复用某种审核结论。
- 为什么要问：MVP 采用“部署方提供项目凭据，主播按需 OAuth 授权”的方式（提案第 3.3 节）。提案明确，不通过多项目规避配额。
- 现有材料：`self-hosting-responsibilities.md` 第 1、3 节列出部署方的职责项。
- 缺口：没有平台结论。Cloud 项目编号尚未创建或提供（提案第 15.3 节）。
- 希望得到的答复：审核责任的归属，审核覆盖是否延伸到各部署方的项目，以及审核结论能否复用。

### Q5 下游输出与 API 数据的再提供

- 问题要点：将获准内容发送到主播控制的 OBS 或第三方展示工具，是否触及限制再次提供 API 功能或 API 数据的条款。如何限定输出对象与用途。
- 为什么要问：输出内容限于显示昵称或安全称呼、文本、付费展示信息、翻译和投递标识。不输出稳定平台用户 ID、内部评分、名单、完整审核理由（提案第 13.1 节）。协议设计不得发展成公开的 YouTube 数据代理或通用转售接口（第 15.2 节）。
- 现有材料：`data-processing.md` 第 7 节的输出字段范围。
- 缺口：输出是否需要额外限制，未经平台确认。开发者政策 III.I.15 已在全文中核对（页面 Last updated 2026-11-06 UTC）：不得提供让用户直接或间接访问 YouTube API 服务所提供数据或功能的 API 服务。该条是否适用于本项目的下游输出，未经平台确认。
- 希望得到的答复：当前输出对象与用途限制是否足够，是否需要额外声明或技术限制。

### Q6 外部 AI 服务与数据处理条款

- 问题要点：使用外部 AI 服务处理必要消息文本，需要哪些披露、数据处理条款和提供方留存约束。
- 为什么要问：AI 任务只发送任务说明、规则摘要、临时 `itemId`、必要消息正文和有限上下文，不发送平台用户 ID、稳定昵称索引、凭据或分数账本（提案第 8.1 节）。临时 ID 是假名化措施，不能证明正文匿名。VoxWard 不长期保存完整对话，但这是应用侧承诺，不等于提供方零留存（第 8.4 节）。
- 现有材料：`data-processing.md` 第 6 节的外部 AI 披露草稿。
- 缺口：所选 AI 服务的实际留存与训练选项尚未核对。部署页面展示的文字尚未确定。
- 希望得到的答复：这类处理需要的披露形式和条款，以及平台对提供方留存的要求。

## 2. 提问前的共同事实

- 产品边界：Middleware，由主播或其受托方自托管在远端服务器，不做官方托管，不跨主播或跨平台共享信誉（提案第 1、1.1、2.2 节）。
- 数据来源：消息只从 YouTube 官方直播聊天接口获取，下游软件不上传弹幕（提案第 1.1、3.1 节）。
- 当前状态：提案第 15.3 节记录，本次申请没有配额扩展需求，没有收到平台重新审核通知，表单为未完成草稿且未提交。
