## 2. YouTube 凭据与 OAuth

依据提案第 3.3 节。

- 常规准备是 Google 账号、Google Cloud 项目、启用 API 和创建合适的凭据。没有另一个必须先取得的通用“YouTube 开发者身份”证书。
- Cloud 项目、OAuth 应用验证和 YouTube API 合规审核是三件不同的事。
- MVP 的方式是：部署方提供项目凭据，主播按需 OAuth 授权。
- OAuth 回调使用实际部署域名，并准确登记为 HTTPS 地址。
- 应用是否需要验证，取决于请求的权限、用户范围和 Google 的规则。“自托管”不是普遍豁免。
- 测试状态（Testing）下，YouTube 权限授权的有效期问题必须写入部署检查。测试应用不能当作长期生产凭据。
- 不能用内置、公开分发的共享 Client Secret 消除部署门槛。独立部署通常需要有人承担项目和凭据管理，这一门槛真实存在。

提案引用了 OAuth 政策、验证例外和发布状态说明（链接见 `status-and-gaps.md` 第 5 节）。本包未核对这些页面。

部署检查清单（草案，实际部署前逐项确认）：

- [ ] 凭据由哪一方创建，保存在哪里，读取身份是否受限（第 16 节）。
- [ ] OAuth 回调地址与实际域名一致，并已在项目中登记。
- [ ] 请求的权限范围与实际功能对应，并说明各项能力的配额成本（第 3.1 节）。
- [ ] OAuth 应用的发布状态（测试或生产），以及授权有效期的影响（第 3.3 节）。
- [ ] 撤销授权的入口，以及撤销后的数据删除流程（见 `data-processing.md` 第 5.3 节）。
- [ ] 隐私政策链接。目前尚未准备（见 `status-and-gaps.md` 第 1 节）。
- [ ] 配额监测和超限时的显示（第 3.1 节）。

## 3. Cloud 项目与审核覆盖

- 提案的方案：部署方提供项目凭据（第 3.3 节）。
- 未确认的问题：软件项目与每个部署方 Cloud 项目的审核责任和覆盖范围，以及审核结论能否复用（第 15.2 节第 4 问，第 20.1 节）。在平台答复前，本包不假定审核结论可以复用。
- 本包不声称存在任何 Cloud 项目编号、审核结论、配额扩展或许可。提案第 15.3 节记录，Cloud 项目编号尚未创建或提供，当前没有配额扩展需求。
- 提案明确，不通过多个项目分散配额（第 3.3 节）。

## 4. 备份、日志与数据请求

- 备份：备份需要有界轮换、权限控制和删除恢复规则（第 12.3 节）。恢复流程必须先重新应用删除记录，才能对外服务（第 12.4 节）。备份中的相关数据应在适用期限内失效，或完成可验证的清理。部署方需要设置轮换期限，并在恢复后验证删除结果。
- 日志：日志分为 Change Log 和 Technical Log 两类（第 12.1 节）。查看器只按授权范围展示内容。日志不向下游开放，也不提供公开或批量下载接口（第 11.2、12.2 节）。
- 关联关系：关联条目不延长保留期限，也不允许重建已删除的数据（第 12.2 节）。删除索引覆盖日志中的关联条目（第 11.3 节）。
- 数据请求：受理、核验、执行、失败和完成状态分别显示。核验不只凭显示昵称，并尽量少收集额外资料（第 11.2 节）。
- 最小审计记录：请求核验、执行状态、删除范围和完成时间（第 10 节数据组表）。删除完成后，Change Log 保留不含消息正文和历史分数的最小处理凭证（第 11.3 节）。
- 需要交付给观众的数据，由获授权的服务器管理工具生成（第 11.2 节）。
